## 1. 项目概述

### 1.1 项目基本信息

| 项目名称 | 基于 AI 驱动的软件工程一体化度量与协作平台 |
|----------|-------------------------------------------|
| 项目简称 | DevInsight |
| 开发单位 | 软件工程实验室 |
| 开发周期 | 2026年3月 — 2026年6月 |
| 项目性质 | 实验室课题研究 |

### 1.2 项目背景

在现代软件工程实践中，团队面临着代码质量难以量化、工程数据分散、AI 辅助工具集成成本高等挑战。现有的工程管理工具（如 SonarQube、CodeClimate）虽然提供了代码质量分析能力，但普遍存在以下不足：

1. **功能单一**: 专注于质量分析，缺乏活度度量、AI 问答、专家识别等能力
2. **部署复杂**: 需要配置独立的数据库和应用服务器
3. **成本高昂**: 商业许可证费用高，开源版本功能受限
4. **AI 集成弱**: 缺乏对 RAG（检索增强生成）等 AI 技术的深度集成

DevInsight 项目旨在构建一个集数据度量、AI 分析、看板协作于一体的轻量级开源平台，填补这一空白。

### 1.3 项目目标

- **P0（核心）**: 实现 GitHub 仓库数据同步、度量计算、质量分析、AI 问答
- **P1（重要）**: 实现增量同步、健康评分、代码热点、专家识别、周报生成
- **P2（增强）**: 实现 CI 监控、风险检测、向量检索、多语言质量分析

## 3. 技术总结

### 3.1 技术选型评估

| 选型 | 选择 | 评价 |
|------|------|------|
| 后端语言 | C++17 | 性能优异，编译产物小巧(单 exe)，但开发效率低于脚本语言 |
| HTTP 框架 | cpp-httplib | 单头文件，零配置，满足小型服务需求 |
| 数据库 | SQLite3 | 嵌入式零维护，适合单机部署，无需独立 DB 服务 |
| 前端框架 | Vue 3 + Vite | 轻量、开发体验好，构建产物为静态文件 |
| AI 接口 | OpenAI 兼容 API | 兼容性好，支持多种大模型提供商 |
| 包管理 | vcpkg | Windows 下 C++ 依赖管理的主流选择 |

### 3.2 架构设计亮点

**1. 增量同步机制**
采用基于游标的增量同步策略，减少 GitHub API 调用次数，提升同步效率。每次同步记录 Issues/PRs/Commits/Releases 的游标位置，下次只拉取新增或变更的数据。

**2. 混合检索策略**
RAG 检索采用关键词（SQL LIKE）+ 向量（Embedding 余弦相似度）混合策略，在不引入外部搜索引擎的前提下，显著提升语义检索的召回率。

**3. 质量评分算法**
基于严重性加权的对数扣分模型，避免了大量风格类问题线性扣到 0 分的情况，使评分更加合理。

**4. 插件化工具支持**
质量分析子系统采用统一的工具接口，可轻松扩展新的分析工具（当前已支持 6 种），每种工具只需实现"调用→解析→入库"三个步骤。

### 3.3 关键技术指标

| 指标 | 实测值 |
|------|--------|
| 知识库检索（万级知识块） | < 1s |
| 质量分析（cppcheck，200 文件） | ~30s |
| 增量同步（10 个仓库） | ~2min |
| 单 exe 体积 | ~5 MB |
| 数据库初始大小 | ~100 KB |

### 4.2 优点与亮点

1. **单 exe 部署**: 后端编译后仅一个可执行文件，前端为静态文件，部署极简
2. **AI 深度集成**: 将 RAG、向量检索、LLM 生成等 AI 技术有机融入工程管理
3. **数据驱动**: 所有功能基于结构化数据，不依赖人工输入
4. **可扩展性强**: 模块化设计，新增工具/功能只需添加新源文件
5. **成本低廉**: 全部组件为开源许可，零商业许可证费用

### 4.3 不足与改进方向

1. **前端 UI 待打磨**: 当前 UI 偏功能导向，美观度与交互体验可进一步提升
2. **缺少用户认证**: 当前为单用户模式，不支持多用户登录和权限控制
3. **无定时调度**: 同步、质量分析等任务需要手动触发，缺少定时调度能力
4. **SQLite 并发限制**: 单机 SQLite 在高并发写入时存在锁竞争
5. **测试覆盖不足**: 缺少自动化测试用例

### 4.4 改进建议

**短期（1-2 个月）**:
1. 增加用户认证和登录页面
2. 添加定时任务调度（cron 表达式）
3. 前端 UI 重构（使用 Element Plus 或 Naive UI）
4. 增加自动测试（单元测试 + API 集成测试）

**中期（3-6 个月）**:
1. 支持多数据源（GitLab / Gitee）
2. 增加告警通知（邮件 / Webhook）
3. 支持自定义度量指标
4. 性能优化（数据库连接池、缓存）

**长期（6 个月以上）**:
1. 支持 PostgreSQL 等独立数据库
2. 微服务化架构拆分
3. ML 模型驱动的缺陷预测

## 6. 经验与教训

### 6.1 成功经验

1. **C++ + SQLite 的轻量组合非常适合小型服务端应用**
   - 单 exe 部署，零运维成本
   - 编译产物跨平台（Windows / Linux）
   - 性能满足中小规模场景

2. **RAG 架构是 AI 工程化的有效路径**
   - 知识库检索可控、可追溯
   - 不依赖 LLM 的训练数据
   - 支持降级（LLM 不可用时检索仍可用）

3. **渐进式增量开发策略有效**
   - 先实现核心功能（同步+度量），再逐步扩展 AI 和质量能力
   - 每个迭代都有可运行的交付物

### 6.2 改进教训

1. **数据库设计前期规划不足**
   - 多次 ALTER TABLE 迁移，存在兼容风险
   - 应提前梳理所有模块的表需求

2. **文档滞后于代码**
   - 前期 API 开发时未同步更新文档
   - 后续应建立"开发即更新文档"的规范

3. **缺少统一错误码体系**
   - 各模块的错误返回格式不一致
   - 前期应定义统一的错误码与响应格式
