# 可行性研究报告

## 1. 引言

### 1.1 编写目的
本报告旨在分析「基于 AI 驱动的软件工程一体化度量与协作平台」（DevInsight）项目的可行性，从技术、经济、操作和法律等多个维度评估项目实施的可行性，为项目立项与投资决策提供依据。

### 1.2 项目背景
软件开发和维护过程中，团队常常面临以下痛点：
- 难以快速掌握项目代码质量状况
- 缺乏可视化的度量指标与趋势分析
- AI 辅助工程分析能力分散，接入成本高
- 代码 review 缺乏结构化数据支撑

本项目旨在构建一个集数据度量、AI 分析、看板协作于一体的平台，帮助团队高效管理工程质量。

### 1.3 项目范围
项目覆盖以下核心子系统：
- 仓库数据同步（GitHub Issues / PRs / Commits / Releases）
- 仓库活跃度与健康评分
- 代码质量静态分析（C/C++/Python/Java）
- AI 智能问答（RAG 检索增强生成）
- 自动周报生成与隐形专家识别
- CI 健康监控
- 风险管理与告警
- 系统日志与 AI 用量统计

## 2. 技术可行性

### 2.1 技术架构
- **后端**: C++17 + cpp-httplib（HTTP 服务器）+ SQLite3（嵌入式数据库）
- **前端**: Vue 3 + Vite + Vue Router（SPA 应用）
- **AI 集成**: OpenAI 兼容 API（支持 DeepSeek / 通义千问 / Ollama 等）
- **向量检索**: 通过 Embedding API 实现语义搜索，降级为关键词检索

### 2.2 关键技术验证

| 技术点 | 状态 | 说明 |
|--------|------|------|
| GitHub REST API 数据同步 | ✅ 已验证 | Issues / PRs / Commits / Releases 全量+增量同步 |
| 增量同步机制 | ✅ 已验证 | 基于游标（cursor）的增量拉取策略 |
| 静态分析工具集成 | ✅ 已验证 | cppcheck / clang-tidy / cpplint / flawfinder / pylint / checkstyle |
| RAG 检索增强生成 | ✅ 已验证 | 关键词+向量混合检索，支持多模型 |
| 知识库构建 | ✅ 已验证 | 从 Issues / PRs / Commits / Releases / 代码提取知识块 |
| PageRank 专家识别 | ✅ 已验证 | 基于协作图与 review 关系的隐形专家发现 |
| 自动周报生成 | ✅ 已验证 | 聚合最近 7 天数据 + LLM 生成 |
| CI 健康监控 | ✅ 已验证 | GitHub Actions Workflow Runs 抓取与分析 |
| 风险检测 | ✅ 已验证 | Code Churn / Issue Backlog / PR Merge Latency 异常检测 |
| 系统日志 | ✅ 已验证 | 操作日志与 AI 用量记录与统计 |
| 跨平台编译 | ✅ 已验证 | Windows MSVC + Linux GCC/Clang 双平台支持 |

### 2.3 技术风险与对策
| 风险 | 影响 | 对策 |
|------|------|------|
| GitHub API 速率限制 | 大规模同步可能触发限流 | 支持分批同步与增量模式，可配置代理 |
| LLM 服务不可用 | AI 问答功能降级 | 知识库检索可独立使用，不依赖 LLM |
| 静态分析工具安装复杂 | 用户可能跳过配置 | 默认只启用核心工具，缺失工具自动跳过并提示 |
| SQLite 并发写入 | 高并发场景下写入锁争用 | 使用 WAL 模式，单线程写入队列 |

## 3. 经济可行性

### 3.1 开发成本分析
项目为校内实验室项目，主要成本如下：

| 成本项 | 说明 | 估算 |
|--------|------|------|
| 人力成本 | 4 名开发人员，周期约 3 个月 | 实验室资源，无额外支出 |
| 基础设施 | GitHub 仓库、本地开发环境 | 免费 |
| LLM API 费用 | 调用大模型 API（DeepSeek / 通义千问） | 按量计费，测试阶段成本可控 |
| 软件许可 | 所有依赖库均为开源许可（MIT / Apache 2.0 / BSD） | 无额外费用 |

### 3.2 收益分析
- 提升团队代码 Review 效率 30%+
- 降低新成员上手成本（AI 问答 + 文档化）
- 减少因代码质量退化导致的返工
- 提供数据驱动的工程管理决策支撑

### 3.3 投资回报
项目以开源形式发布，核心价值在于：
- 降低团队工程管理工具链的搭建成本
- 提供 AI 驱动的工程分析能力，替代人工审计
- 支持私有化部署，数据不出域

## 4. 操作可行性

### 4.1 用户操作流程
1. **部署**: 解压发布包 → 修改配置文件 → 双击启动（约 5 分钟）
2. **注册仓库**: 在平台界面输入 GitHub 仓库名
3. **同步数据**: 一键同步 Issues / PRs / Commits
4. **质量分析**: 选择工具后运行静态分析
5. **查看报告**: 在仪表盘查看评分、趋势、热点
6. **AI 问答**: 输入问题，获取带证据引用的智能回答

### 4.2 用户技能要求
- **管理员**: 具备基本 Git 和命令行操作能力
- **普通用户**: 仅需浏览器操作，无需编程知识

### 4.3 部署环境要求
| 环境 | 最低要求 | 推荐配置 |
|------|----------|----------|
| 操作系统 | Windows 10 / Ubuntu 20.04 | Windows 11 / Ubuntu 22.04 |
| CPU | 2 核 | 4 核以上 |
| 内存 | 4 GB | 8 GB |
| 磁盘 | 2 GB 可用空间 | 10 GB（含仓库缓存） |
| 网络 | 可访问 GitHub 和 LLM API | 稳定宽带连接 |

## 5. 法律可行性

### 5.1 许可证合规性
- 项目自身采用开源许可证发布
- 使用的第三方库均兼容商用/教育用途（MIT、Apache 2.0、BSD、Public Domain）
- 依赖的 vcpkg 包管理器为 MIT 许可

### 5.2 数据合规
- 仓库数据来源于 GitHub 公开 API，符合 GitHub Terms of Service
- 用户 GitHub Token 仅用于 API 认证，不传输至第三方
- LLM API 调用仅发送问题与检索上下文，不发送原始 Token

### 5.3 知识产权
- 项目为原始开发成果
- 使用的 PageRank 算法为公开算法
- 前端 UI 为自主设计

---

## 6. 结论

**项目可行**，建议启动开发。理由如下：

1. **技术可行性高**: 核心技术已在原型中验证通过，关键功能全部可工作
2. **经济成本低**: 基于开源技术栈，无需昂贵商业许可证
3. **操作门槛低**: 一键部署+浏览器操作，非技术人员也可使用
4. **法律风险低**: 合规使用开源组件，无版权争议
5. **价值明确**: 填补了「AI 驱动工程度量」领域的开源工具空白
