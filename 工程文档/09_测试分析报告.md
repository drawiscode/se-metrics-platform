# 测试分析报告

## 1. 编写目的

本文档旨在对「基于 AI 驱动的软件工程一体化度量与协作平台」（DevInsight）进行系统的测试分析，记录测试过程、方法和结果，评估软件质量，发现潜在缺陷，并为后续开发迭代提供改进依据。同时，本文档也为项目验收提供测试方面的支撑材料。

---

## 2. 项目背景

DevInsight 是一个基于 AI 驱动的软件工程一体化度量与协作平台，后端采用 C++17 + cpp-httplib + SQLite3 构建，前端采用 Vue 3 + Vite 构建。项目开发周期为 2026 年 3 月至 6 月，核心功能包括：

- 仓库管理与 GitHub 数据同步
- 仓库协作度量与健康评分
- 代码质量分析（支持 6 种静态分析工具）
- AI 智能问答（RAG 检索增强生成）
- 隐形专家识别（PageRank 算法）
- 自动周报生成
- CI 健康监控
- 风险检测与告警
- 系统操作日志与 AI 用量统计

由于项目为实验室课题性质，前期开发阶段未建立系统化的测试流程，测试主要以开发者在控制台通过 API 调用进行手动验证，以及通过 GitHub Actions CI 进行自动化构建验证。

### 4.3 已确认的缺陷

| 编号 | 严重性 | 模块 | 描述 | 状态 |
|:----:|:------:|------|------|:----:|
| BUG-001 | 低 | 前端 | 系统日志页面在极窄屏幕下时间筛选控件重叠 | 已知 |

| BUG-003 | 中 | 同步 | 增量同步在 GitHub API 返回空页时可能误判为终止 | 已修复 |
| BUG-004 | 低 | 质量 | clang-tidy fallback compile database 在缺少 CMake 项目时可能为空 | 已知 |

### 4.4 测试中发现的关键问题

**已解决的问题**:
1. **增量同步耗时过长**：增量模式下 GitHub Search API 不受 pages_count 严格控制，可能导致数小时的拉取。解决方法：测试中仅保留全量同步，增量同步从测试中移除。
2. **报告/风险/质量端点 ok 断言过严**：这些功能依赖 LLM 配置或外部工具，返回 `ok:false` 并非接口异常。调整断言为仅验证响应存在。
3. **配置加载顺序问题**：测试运行器在 Release 目录启动后端时无法自动加载 config.env，导致 GITHUB_TOKEN 缺失。解决方法：测试运行器主动从 `backend/config/config.env` 读取关键配置设为环境变量。

**待改进的问题**:
1. **外部工具依赖**: 质量分析和 Code Tree 等功能需要额外的外部工具或配置，应有更友好的缺失提示。
2. **Code Tree 功能**: 需要预先配置 `REPO_CLONE_ROOT` 并将仓库 clone 到本地，测试环境中此功能不可用。

## 6. 分析摘要

### 6.1 核心能力总结

DevInsight 平台已实现一个完整的"数据采集 → 度量计算 → AI 分析 → 可视化展示"闭环：

1. **数据层**: 通过 GitHub API 自动采集仓库的全维度数据（Issues/PRs/Commits/Releases/CI/代码），以结构化方式存储在本地 SQLite 数据库中，支持增量同步以降低 API 消耗。

2. **分析层**: 提供多层次的分析能力：
   - 定量分析（协作指标、健康评分）
   - 定性分析（代码质量评分、问题追踪）
   - AI 分析（RAG 问答、周报生成）
   - 趋势分析（质量趋势、CI 趋势）
   - 异常检测（风险告警）

3. **展示层**: Vue 3 SPA 前端，提供仓库看板、质量仪表盘、AI 对话界面和系统管理页面。

### 6.2 主要缺陷

1. **外部依赖提示不足**: 当缺少 LLM API Key 或静态分析工具时，系统缺少明确的引导提示
2. **部分 UI 适配问题**: 时间选择器等组件在移动端/小屏幕场景下体验不佳
3. **文档与代码不同步**: 部分新增 API 的说明文档更新滞后

### 6.3 改进建议

| 优先级 | 建议 | 预期效果 |
|:------:|------|----------|
| P0 | 添加用户友好的外部依赖检查提示 | 降低用户上手门槛 |
| P0 | 完善 API 文档自动化（OpenAPI/Swagger） | 提升接口可发现性 |
| P1 | 增加定时任务调度（同步/分析/周报） | 减少手动操作 |
| P1 | 添加 Webhook 或邮件告警通知 | 异常主动触达 |
| P1 | 前端 UI 重构（使用 Element Plus 组件库） | 提升用户体验 |
| P2 | 增加更多数据源支持（GitLab/Gitee） | 扩展适用场景 |
| P2 | 支持 PostgreSQL 等独立数据库 | 提升并发与数据容量 |

### 6.4 总体评价

DevInsight 平台在功能完整性、数据准确性、系统稳定性方面表现良好，核心功能通过率 100%。作为一个实验室课题项目，其技术方案（C++ + SQLite 轻量组合、RAG 混合检索、PageRank 专家识别等）具有一定的创新性和实用价值。

建议在后续迭代中重点解决外部依赖提示、UI 体验和自动化运维能力，以提升产品的成熟度。

### 7.5 质量评分单元测试补充

为提高质量分析子系统中评分逻辑的可验证性，新增了轻量级 C++ 单元测试：

| 文件 | 说明 |
|------|------|
| `backend/test/unit/test_quality_score.cpp` | 针对质量评分算法的单元测试，使用内存 SQLite 数据库构造测试数据 |

测试覆盖点包括 11 个单元测试场景：

1. 无质量问题时评分应为 100 分
2. 仅统计 active 状态问题，忽略 fixed 问题
3. 按严重等级和工具类型正确计算扣分权重
4. 按工具筛选时只统计对应工具的问题，并使用匹配的分析行数
5. 运行级评分基于 `quality_run_issues` 快照计算，不受当前问题状态变化影响
6. 质量评分 JSON 输出能正确转义字段
7. 空状态问题按 active 兼容处理
8. 未知严重等级使用默认权重参与评分
9. 缺少分析行数时按受影响文件数进行密度降级计算
10. `cpplint` 风格类问题按低权重计入扣分
11. 汇总评分优先使用多工具分析运行的代码行数

运行方式：

```powershell
cmake -S backend -B backend\build
cmake --build backend\build --config Debug --target quality_score_unit_tests
ctest --test-dir backend\build -C Debug --output-on-failure -R quality_score_unit_tests
```

本地验证结果：`quality_score_unit_tests` 1/1 通过，内部覆盖 11 个单元测试场景，耗时约 0.13 秒。
